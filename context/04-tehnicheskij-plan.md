# Технический план радара

Это наш проработанный план от 14.08.2026, вычищенный от внутренних деталей.
Код не написан — план готов, реализации не было. Можно брать как есть, можно
спорить; но каждое решение ниже принято по конкретной причине, причина указана.

---

## Ключевые решения и почему именно так

### 1. Нейросеть в сборе данных НЕ участвует — только в разборе

Обнаружение изменения — это `diff` двух текстовых снимков. Бесплатно,
детерминированно, не выдумывает. LLM нужен ровно на одном шаге: «объясни человеку,
что из этих 40 диффов важно». Этот шаг можно делать вручную в чате с ИИ-ассистентом
по накопленному материалу — отдельный платный ключ на этом этапе не нужен.

**Явно отвергнуто: LLM-скраперы** (`scrapegraphai` и аналоги). Причины:

- Требуют платный ключ на каждую загруженную страницу.
- Шлют телеметрию по умолчанию.
- Решают задачу «понять незнакомую структуру сайта», а у нас 19 знакомых сайтов,
  структура которых меняется раз в квартал. Задача не та.
- Замер зависимостей (`pip install --dry-run`, 14.08.2026): `scrapegraphai` тянет
  **104 пакета** — 7 пакетов langchain, playwright + undetected-playwright, tiktoken,
  tokenizers, весь boto3-стек через langchain-aws. Плюс ~400 МБ браузеров отдельной
  командой. Для diff двух текстов это несоразмерно.

Если когда-нибудь понадобится — ставить только в изолированное виртуальное окружение
и с отключённой телеметрией (переменная окружения `SCRAPEGRAPHAI_TELEMETRY_ENABLED=false`)
**до первого запуска**.

Наш набор без ИИ — 4 пакета: `httpx`, `selectolax` (или `bs4`), `feedparser`, `PyYAML`.

### 2. Сравниваем видимый текст, а не HTML

Сайты на Tilda, React и Next меняют разметку и хеши CSS-классов при каждой пересборке.
Сравнение сырого HTML даст «изменение!» каждый день на всех доменах и убьёт доверие
к системе на первой же неделе.

Нормализация: вытаскиваем видимый текст, схлопываем пробелы, вырезаем заведомо
динамическое — счётчики, «онлайн 47 человек», текущие даты, CSRF-токены, номера
сборки, идентификаторы сессий.

### 3. Дайджест, а не поток

Изменение попадает в дайджест только если затронуто больше N символов видимого
текста. Стартовое значение **120 символов**, калибруется на первой неделе живой работы.
Мгновенный алерт — только для критичного класса (см. [03-chto-otslezhivat.md](03-chto-otslezhivat.md)).

### 4. Первый прогон источника — не изменение, а базовая линия

Иначе в первый день прилетит 19 × 4 «изменений» на пустом месте.

## Фазы

### Фаза 0. Разведка источников

Прежде чем писать сборщик — проверить руками, что каждый источник вообще отдаётся.
Правило, выученное на своих ошибках: **проверять на живых данных, а не по документам.**
Планы про состояние внешних систем протухают за недели.

- Для каждого из 19 конкурентов найти URL: главная, страница тарифов, страница
  интеграций, блог или новости. Часть страниц отсутствует (у Rechka.ai, Imot.io
  и Родника цен нет) — так и фиксировать: «нет».
- Найти их каналы: ВК, Telegram, Дзен, YouTube, VC, Habr. Записать **реальные**
  идентификаторы, проверенные открытием, а не догадки по названию бренда.
- Проверить HTTP-ответ каждого URL: 200 / 403 (бот-защита) / редирект. Домены
  под защитой пометить отдельно — им понадобится браузерная автоматизация вместо
  простого запроса.
- Результат — `sources.yaml`: проверенные URL с пометкой способа обхода.
  Заготовка списка — [data/konkurenty.csv](data/konkurenty.csv).

**Точка принятия решения:** если больше 3 доменов отдают 403 на простой запрос —
пересматривать Фазу 2 в сторону браузерной автоматизации (Playwright) по умолчанию.
Она надёжнее, но обход медленнее и тяжелее по ресурсам.

### Фаза 1. Каркас проекта

Порядок шагов важен: первым идёт `.gitignore`, а не код.

1. **`.gitignore` — раньше `git init` и раньше первого коммита.** В проекте лежит
   `radar/vk_tokens.json` — живой доступ к аккаунту ВК от лица владельца
   (`access_token`, `refresh_token`, `id_token`, `user_id`). Попав в коммит, он
   останется в истории репозитория навсегда: удаление файла следующим коммитом
   его оттуда не убирает, а токен придётся отзывать. Поэтому файл закрывается
   до того, как git вообще появится в папке.
   Туда же — `__pycache__/`, `data/_raw/` (101 HTML-файл, 45 МБ,
   воспроизводимого происхождения), будущие `snapshots/`, `runs/` и `.env`.
   Сами скрипты `vk_token.py` и `tools/check_vk.py` секретов не содержат и в
   репозитории остаются: токен они читают из `vk_tokens.json` или из переменной
   окружения `VK_TOKEN`.
2. **`requirements.txt`** с фактическими версиями с рабочей машины.
   Состав против исходного плана изменён по итогам Фазы 0: `feedparser` не
   нужен (RSS-источников не осталось ни одного), `selectolax` не нужен
   (`beautifulsoup4` вывез все 19 доменов). Добавлен `certifi` — без него
   Python на Windows не проверяет сертификат `vk.com`.
3. **README проекта** — что это, как поставить, как запускать, где лежат
   секреты и почему их нет в репозитории.
4. **Структура папок** под снимки и прогоны: `snapshots/`, `runs/`.
   Папки версионируются, содержимое — нет.
5. **Проверка на утечку — последний шаг фазы, до первого коммита.**
   Одного `.gitignore` мало: правило можно написать так, что оно не сработает.
   Проверяется фактом, а не чтением файла: `git init`, затем `git add -A`
   и просмотр того, что реально попало в индекс; поиск по содержимому индекса
   строк токена, `refresh_token` и `user_id`; проверка, что `git check-ignore`
   подтверждает исключение `vk_tokens.json`. Только после чистого результата —
   первый коммит.

### Фаза 2. Сборщик снимков

- Обход `sources.yaml`, нормализация в видимый текст, сохранение снимка в
  `snapshots/<домен>/<страница>/<ГГГГ-ММ-ДД>.txt`.
- **Вежливость обязательна:** User-Agent с контактным адресом, пауза между
  запросами, `robots.txt` уважаем, таймаут и 2 повтора. Мы наблюдаем публичные
  страницы, а не долбим чужой сайт. Это и этика, и способ не получить блокировку.
- **Устойчивость:** падение одного источника не роняет весь прогон. Итог прогона —
  `runs/<дата>.json` со статусом по каждому источнику отдельно.
- **Хранение:** держим последний снимок плюс историю диффов. Полные снимки старше
  90 дней чистим, иначе хранилище распухает без пользы. Диффы храним всегда —
  они маленькие и в них вся ценность.

### Фаза 3. Детектор изменений

- Сравнение с предыдущим снимком, выдача структурированной дельты: что добавлено,
  что удалено, сколько символов затронуто.
- Шумодав: словарь заведомо динамических фрагментов + порог по объёму.
- **Отдельное извлечение чисел со страниц тарифов** — не «текст изменился»,
  а «было 21 900 ₽ → стало 24 900 ₽». Самый ценный сигнал во всей системе,
  делать его нужно явным разбором, а не общим диффом.

### Фаза 4. Классификация и уведомления

- Классификатор на два класса — критично / обычно (таблица в
  [03-chto-otslezhivat.md](03-chto-otslezhivat.md)).
- Отправка в Telegram через бота. Бот радара должен быть **отдельным**, не общим
  с другими задачами: у разных задач разная критичность, разные права и разная
  частота отказов. Общий бот означает, что поломка в одной задаче гасит алерты
  всех остальных.
- Сборка недельного дайджеста: группировка по конкуренту, строка
  «ничего не менялось у: …» одной строкой (это тоже информация), ссылка на
  источник каждого пункта — чтобы можно было проверить в один клик.

### Фаза 5. Расписание

- Ежедневный сбор. Время — **не на ровном часе**: в :00 очередь у планировщиков
  переполнена и запуск сдвигается непредсказуемо. Ориентир 06:30 UTC.
- Отправка дайджеста — по понедельникам.
- **Health-check обязателен:** если сбор не прошёл 2 дня подряд — алерт владельцу.
  Без этого система тихо умрёт, и выяснится это через месяц.

### Фаза 6. Калибровка на живых данных — не пропускать

Система без этой фазы генерирует шум и умирает.

- Неделя работы в режиме «только копим, дайджест показываем в личном чате, не в
  боевой рассылке».
- По итогам: поднять или опустить порог, дописать шумодав, выкинуть источники,
  которые дают только ложные срабатывания.
- Только после этого включать боевую отправку.

## Риски и что с ними делать

| Риск | Вероятность | Что делаем |
|---|---|---|
| Шум убивает доверие к дайджесту | Высокая | Фаза 6 обязательна, порог калибруется на живых данных |
| Бот-защита на части доменов | Средняя | Точка решения в Фазе 0, запасной путь через браузерную автоматизацию |
| Конкурент меняет структуру сайта → сборщик молча собирает пустоту | Средняя | Проверка: если видимый текст страницы меньше 200 символов — это поломка сборщика, а не «удалили контент». Алерт, а не тишина |
| Токен доступа к соцсети протухает | Известная | Токены мини-приложений живут сутки; для фонового сбора нужен тип приложения, дающий долгий токен. Проверить это ДО того, как строить расписание |
| Хранилище распухает от снимков | Низкая | Чистка полных снимков старше 90 дней, диффы храним всегда |
| Ложное «изменение» из-за динамических блоков | Высокая | Словарь исключений + нормализация текста (решение №2 выше) |
| Токен доступа уезжает в историю git | Средняя | `.gitignore` до `git init`; проверка индекса фактом в конце Фазы 1; секреты только в `vk_tokens.json` и `VK_TOKEN`, никогда в `config.yaml` |

## Грабли, известные по задачам такого типа

Не связано напрямую с радаром, но экономит время в любой системе «собери по
расписанию → сравни → уведоми».

- **Планировщик задач в репозитории работает только из ветки по умолчанию.**
  Расписание в другой ветке молча не запускается.
- **Задание секрета через `stdin` в CLI-утилитах может записать литеральный дефис**
  вместо значения. Выглядит потом как «протухший токен», а на деле секрет пустой.
  Задавать значением и проверять.
- **Ноль — это тоже измерение.** Типовая ошибка: измеренный ноль отбрасывается как
  «нет данных», и график замирает на старом значении вместо честного падения в ноль.
  Различать «не измеряли» и «измерили ноль» надо на уровне модели данных, а не в отчёте.
- **Объём текста мерить по источнику, а не по HTML.** HTML с обвязкой завышает
  объём вчетверо. Ошибка замера превращается в ошибку порога.
- **Проверять на живых данных до починки.** Дважды за одну сессию «сломанное по
  документам» оказывалось рабочим, а починка ломала работающее.

## Если методику будут переносить на другой рынок

Заменяемая часть — только `sources.yaml` и словарь шумодава. Всё остальное
(нормализация текста, диффы, порог, классы срочности, дайджест) от рынка не зависит.

Что переносится один в один:
1. Сбор без ИИ, разбор с ИИ.
2. Сравнение видимого текста, не HTML.
3. Первый прогон = базовая линия.
4. Два класса срочности: цена и продуктовая линейка → мгновенно, всё остальное → в дайджест.
5. Отдельное извлечение чисел с коммерческих страниц.
6. Неделя калибровки перед боевым включением.
7. Health-check на «сбор не прошёл 2 дня» — иначе система умирает незаметно.

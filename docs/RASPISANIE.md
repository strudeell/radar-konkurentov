# Расписание: как радар работает сам

Раньше сбор запускал человек: три команды подряд, каждый день, руками. Этот файл
про то, как передать эту работу компьютеру и как потом убедиться, что он её
делает.

## Что происходит каждый день

В 11:37 по местному времени (06:37 UTC) сторож запусков — планировщик задач в
Windows, launchd в macOS — запускает одну программу, [daily.py](../daily.py).
Дальше она делает всё сама, по порядку:

| Шаг | Что делает | Сколько занимает |
|---|---|---|
| Сбор | обходит 60 источников, снимает страницы | около 3 минут |
| Разбор | сравнивает со вчерашним, находит изменения | меньше секунды |
| Уведомления | срочное отправляет сразу, обычное копит | секунды |
| Сводка | по понедельникам — недельная сводка в Telegram | секунды |
| Здоровье | проверяет, идёт ли сбор вообще | мгновенно |

Окна на экране при этом не появляется. В Windows задача запускается через
`pythonw.exe`, который работает молча; в macOS launchd и так запускает всё без
окна. Весь вывод пишется в `work/logs/<дата>.log` — туда и надо смотреть, если
что-то пошло не так.

## Как поставить

Установщик свой на каждую систему, но команд в нём одинаково четыре: поставить,
посмотреть, запустить сейчас, снять. Настройки оба берут из одного места — из
[config/config.yaml](../config/config.yaml), раздел `schedule`, — и спрашивают
их у самого радара командой `daily.py --plan`. Поэтому время правится в одном
файле, а не в двух местах на двух системах.

### Windows

Из папки `radar`, в PowerShell:

```
powershell -ExecutionPolicy Bypass -File tools\schedule.ps1 -Action install
```

Ключ `-ExecutionPolicy Bypass` нужен потому, что Windows по умолчанию не
запускает скрипты PowerShell, скачанные или созданные программой. Он действует
только на этот один запуск и ничего в системе не меняет.

Проверить, что задача встала:

```
powershell -ExecutionPolicy Bypass -File tools\schedule.ps1 -Action status
```

Скрипт покажет время запуска, когда прогон был последний раз, с каким кодом
завершился и когда будет следующий. Задача видна и в самом планировщике —
`Win+R`, `taskschd.msc`, имя `RadarKonkurentov`.

Запустить прогон прямо сейчас, не дожидаясь завтра:

```
powershell -ExecutionPolicy Bypass -File tools\schedule.ps1 -Action run
```

Снять задачу:

```
powershell -ExecutionPolicy Bypass -File tools\schedule.ps1 -Action remove
```

Снимки, диффы, журналы отправок и настройки остаются на месте — снимается только
ежедневный запуск.

### macOS

Из папки `radar`, в Терминале:

```
bash tools/schedule.sh install
```

Обходить запреты не нужно: macOS не мешает запускать свои же скрипты. Задачу
ставит launchd — штатный сторож запусков; файл задачи он кладёт в
`~/Library/LaunchAgents/ru.okk-ai.radar.plist`.

Проверить, что задача встала:

```
bash tools/schedule.sh status
```

Покажет время запуска, каким Python задача запускается, где лежит файл задачи и
с каким кодом закончился последний прогон. Задача видна и системе:
`launchctl list | grep ru.okk-ai.radar`.

Запустить прогон прямо сейчас, не дожидаясь завтра:

```
bash tools/schedule.sh run
```

Снять задачу:

```
bash tools/schedule.sh remove
```

Есть пятая команда, которой нет в Windows-версии, — посмотреть готовый файл
задачи, ничего не устанавливая:

```
bash tools/schedule.sh plist
```

**Одна ловушка macOS, из-за которой расписание молча не работает.** Начиная с
macOS 13, фоновая задача не получает доступа к «Рабочему столу», «Документам» и
«Загрузкам», даже если запущена от вашего имени. Если папка `radar` лежит там,
прогон упадёт на первом же снимке, а причина в сообщении будет выглядеть как
что угодно, только не как запрет доступа. Лечится двумя способами: держать папку
вне этих трёх мест (например, `~/radar`) или выдать Полный доступ к диску
Терминалу в «Системных настройках» → «Конфиденциальность и безопасность».

## Что человек получит и когда

Ничего не изменилось по сравнению с Фазой 4, изменился только тот, кто нажимает
кнопку:

- **Срочное** — сразу в день, когда нашлось: цена, тарифная линейка, объявление
  о смене условий.
- **Обычное** — одной сводкой в понедельник утром, после того как пройдёт
  понедельничный сбор. Если понедельник пропущен — машина была выключена, —
  сводка досылается в первый же день, когда радар очнулся. А вот за неделю, в
  которую радар не собрал ни одного дня, сводки не будет вовсе: пустая сводка
  читается как «у конкурентов тихо», а это неправда.
- **«Радар не собирает»** — если сбор не прошёл два дня подряд. Это новое, и
  ради этого фаза во многом и делалась.

Больше радар не пишет ничего. Ежедневного «изменений нет» не будет: система,
которая пишет каждый день, перестаёт читаться к концу второй недели.

## Если пришла красная тревога

Сообщение выглядит так:

```
🔴 Радар: сбор не проходит 2 дня подряд

18 августа — прогона не было
19 августа — снято только 10 из 60

Последний удачный сбор: 17 августа.
```

Порядок разбора — от самого частого к самому редкому:

1. **Посмотреть журнал последнего прогона:** `work/logs/<дата>.log`. В нём построчно
   видно, на чём споткнулся сбор.
2. **Запустить руками:** `python daily.py`. Если руками работает, а по
   расписанию нет — дело в задаче, смотреть её состояние командой `status`.
3. **Проверить доступы.** Токен ВКонтакте живёт около часа и обновляется сам,
   но обновление тоже может перестать работать: `python tools/check_vk.py`.
   Бот Telegram: `python notify.py --check`.
4. **Проверить, была ли машина включена.** Самая частая причина «прогона не
   было» — не поломка, а выключенный компьютер.

Когда сбор пойдёт снова, радар сам пришлёт зелёное сообщение и скажет, сколько
дней молчал.

## Чего расписание не умеет

Четыре ограничения. Они известны заранее, и лучше знать про них до первого
сюрприза.

**Выключенная машина ничего не собирает.** Планировщику сказано «запусти
пропущенное, как только сможешь», поэтому прогон случится сразу после включения
компьютера, а не пропадёт. Но если компьютер не включали три дня, за эти три дня
снимков нет и взять их неоткуда: чужой сайт не хранит вчерашнюю версию себя.
Радар в этом случае честно скажет, что молчал, а не сделает вид, что у
конкурентов было тихо.

**Задача работает только от вошедшего в систему владельца.** Windows умеет
запускать задачи и без входа, но за это просит сохранить пароль учётной записи
на диске. В macOS то же самое и по той же причине: задача ставится в
`LaunchAgents`, то есть живёт в сеансе владельца, а не в системе. Ради
ежедневного обхода публичных страниц пароль на диске — плохая сделка: секрет
всей учётной записи крупнее, чем всё, что радар охраняет. Цена решения: если в
компьютер не входили сутки, прогон подождёт входа.

**В macOS нет повтора через двадцать минут.** Windows-планировщику сказано:
если прогон вернул ошибку, повтори дважды с интервалом в двадцать минут — чаще
всего виновата лежащая сеть, и через двадцать минут она уже поднялась. launchd
такого не умеет: он либо перезапускает задачу сразу и бесконечно, либо не
перезапускает вовсе, и первое здесь хуже болезни — это стук в чужие сайты по
кругу. Поэтому в macOS-версии повтора нет. Прикрывает это проверка здоровья: на
второй день без сбора радар сам поднимает тревогу.

**Сам себя из могилы радар не поднимет.** Health-check живёт внутри прогона:
если прогон не запускается вовсе — например, задачу отключили или снесли, —
сообщать о поломке некому. Это не недосмотр, а свойство любого сторожа, который
живёт в том же доме, что и охраняемое. Частично лечится тем, что первый же
состоявшийся прогон расскажет про весь пропуск задним числом; полностью — только
внешним сторожем на другой машине, а его в этом проекте нет.

## Почему именно так

**Почему планировщик Windows, а не облако.** Секреты радара лежат на этой
машине и в репозиторий не попадают. Облачное расписание означало бы завести те
же секреты ещё в одном месте. Плюс в плане отдельной строкой записаны грабли:
расписание в репозитории запускается только из ветки по умолчанию и в любой
другой молча не работает.

**Почему 11:37, а не 11:30 и не полдень.** План требовал «не на ровном часе»:
у облачных планировщиков в :00 очередь переполнена и запуск уезжает на
непредсказуемое время. Здесь планировщик свой и очереди у него нет, но соседи
есть: на ровных получасах просыпается автообслуживание Windows и обновления. За
сеть и диск с ними лучше не соревноваться. Время задаётся в
[config.yaml](../config/config.yaml), в разделе `schedule`, по UTC — установщик сам
пересчитает его в местное.

**Почему одна программа, а не три задачи в планировщике.** Планировщик умеет
запустить программу и не умеет «если сбор упал — разбор не запускай» и «по
понедельникам ещё и сводку». Три задачи означали бы три места, где это может
разъехаться. Здесь у планировщика одна строка, а порядок и условия — в
[daily.py](../daily.py), рядом с объяснением, почему они такие.

## Куда смотреть

| Где | Что там |
|---|---|
| `work/logs/<дата>.log` | весь вывод прогона за день. Чистится через 90 дней |
| `work/runs/<дата>.json` | итог обхода источников за день (Фаза 2) |
| `work/runs/health.json` | память health-check: о какой тревоге уже сказали |
| `python daily.py --health` | здоровье сбора за последние две недели, ничего не запуская |
| `python tools/schedule_check.py` | проверка правил тревоги на выдуманных днях |
